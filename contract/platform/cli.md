# 量潮命令行工具章程

## 第一章 总则

**第一条 制定依据**
本章程依据《量潮软件工程章程》制定，参照 Google 命令行工具实践：[Fuchsia 命令行界面规范](https://fuchsia.googlesource.com/fuchsia/+/main/docs/development/api/cli.md)、[Google Cloud CLI 命令约定](https://cloud.google.com/sdk/gcloud/reference/topic/command-conventions)、[Google 开发者文档风格指南](https://developers.google.com/style/code-syntax)与 [Abseil 选项指南](https://abseil.io/docs/python/guides/flags)，规范量潮命令行工具的设计、输出与演进。

**第二条 适用范围**
本章程适用于量潮科技所有面向人与机器调用的命令行工具，包括平台 CLI（如 `qtcloud-execute`、`qtcloud-work`）、运维脚本入口与工具箱可执行文件。库的内部 API 不在本章程约束范围内。

**第三条 基本原则**

（一）**可脚本化**。命令行工具的首要消费者是脚本与 AI，其次才是人。默认不交互、输出可解析、退出码可判断，任何需要人盯屏才能使用的工具视为不合格。

（二）**一致优先**。同类工具使用相同的命令结构、选项名与输出约定。一致性比个别工具的最优设计更重要——用户学会一个工具，就应能推断其余工具。

（三）**人类默认，机器可选**。默认输出面向人阅读，机器可读输出由显式选项（如 `--json`）开启，二者不混排。

（四）**最小惊讶**。命令做什么、参数如何解释，应与通行 Unix 惯例和同族工具保持一致，不发明私人语法。

## 第二章 命令结构

**第四条 命令命名**

（一）命令以**动词优先**表达动作，例如 `health`、`create`、`list`、`delete`；需要分组时按资源组织命令组，形如 `<工具> <资源组> <动词>`。

（二）命令名使用小写英文单词，多个单词用连字符分隔（`list-tasks`），不使用下划线、缩写与拼音。

（三）动词在同一工具内不得混用同义词，例如不得同时出现 `list` 与 `ls`、`delete` 与 `remove`。缩写仅在成为通行惯例时使用（`ls`、`rm`）。

**第五条 位置参数**
位置参数**至多一个**，用于标识命令作用的对象（如清单 ID、任务 ID）；其余输入一律以选项表达。多个位置参数会让命令难以阅读与扩展，应禁止。

**第六条 选项**

（一）选项使用长格式 `--kebab-case`，含义自描述；只有 `-h`、`-v` 等通行惯例才提供短格式。

（二）布尔选项不取值：`--json` 表示开启，`--no-json` 表示关闭；不得要求 `--json=true` 这类写法。

（三）选项取值用 `--server <URL>` 或 `--server=<URL>` 两种写法，二者必须等价。

（四）全局选项（如 `--server`、`--json`、`--quiet`）在所有子命令中语义相同，并使用相同名称；局部选项不得与全局选项重名。

**第七条 标准选项**
下列选项在量潮命令行工具中使用统一定义：

- `--help`（`-h`）：打印帮助并退出，退出码为零
- `--version`（`-V`）：打印版本号并退出，版本号取自包清单
- `--verbose`（`-v`）：增加诊断输出，诊断写入标准错误
- `--quiet`：抑制非必要输出，只保留结果与错误
- `--json`：以 JSON 输出，直接透传服务端或结构化结果
- `--yes`：跳过确认提示，供脚本使用

## 第三章 输出与交互

**第八条 输出流**
标准输出只放命令结果，日志、进度与错误一律写入标准错误。管道中 `tool | jq` 必须只收到数据，收到的任何提示文字都视为缺陷。

**第九条 输出格式**
默认输出面向人阅读：信息分列、无冗余装饰、必要时有表头。机器可读输出由 `--json` 提供，字段名与服务端契约一致，不额外包裹自定义结构。

**第十条 交互**

（一）默认不提示。仅在标准输入与输出均连接终端且有真实风险时才允许确认，例如删除、覆盖、发布。

（二）危险操作必须支持 `--yes` 跳过确认，使脚本与 AI 可以无人值守执行；未提供跳过方式的高风险操作视为设计缺陷。

（三）不得用分页器、进度动画等阻塞管道执行；此类行为只能在检测到终端时启用。

**第十一条 退出码与错误**
成功退出码为零，失败为非零。错误消息写入标准错误，格式为「错误: <原因>」，并在可行动时给出下一步建议；不得只打印栈追踪而不说明补救方式。

## 第四章 帮助与文档

**第十二条 帮助文本**
`--help` 必须可用，且包含工具用途一句话、用法概要、全部子命令与选项说明（含默认值）、至少一个真实示例。帮助文本随功能同步更新，过时帮助等同缺陷。

**第十三条 命令语法书写**
在文档中书写命令语法遵循以下约定：方括号 `[]` 表示可选，竖线 `|` 表示互斥，大写下划线表示占位符（如 `LIST_ID`），省略号 `...` 表示可重复；示例使用可直接运行的完整命令，不含提示符。

## 第五章 兼容与演进

**第十四条 稳定性**
已发布命令与选项的行为属于对外契约，不得静默改变。实验性能力须显式标注（如 `alpha`、`beta` 子命令或选项），并声明可能变更。

**第十五条 破坏性变更**
优先新增选项而非改变既有语义。确需破坏兼容时，先提供新写法并标记旧写法为弃用，在变更记录中说明迁移方式，保留期结束后移除。

**第十六条 幂等与安全**
查询类命令必须幂等，可重复执行；写入类命令应支持幂等重放或在文档中说明重复执行的后果。默认值取安全一侧，危险默认必须显式声明。
